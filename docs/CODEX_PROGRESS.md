# تقدم إطلاق رافد MVP

آخر تحديث: 26 يوليو 2026

## وصف مختصر للمشروع

رافد V4.3 منصة عربية لتقييم جاهزية المشاريع لفرصة تمويل محددة. تستخرج شروط الفرصة وبيانات المشاريع، تتحقق من الأهلية والأدلة، ثم تنتج سجل فجوات وخطة إغلاق وحزمة قرار مؤسسي. النتيجة أداة دعم قرار وليست وعدًا بالتمويل، وتبقى المراجعة البشرية إلزامية.

## التقنية الحالية بعد الاكتشاف

- JavaScript بنمط CommonJS على Node.js `>=20.16 <23`، مع HTML وCSS وSQL وPowerShell.
- واجهة ثابتة بلا إطار عمل: `frontend/index.html` و`frontend/rafid-v4.js` و`frontend/rafid-v4.css`.
- خادم Node موحد مبني على `node:http` في `scripts/run-rafid.js`، ومسار نشر بديل عبر Azure Functions v4 في `src/index.js` و`src/functions/`.
- npm هو مدير الحزم، و`package-lock.json` موجود.
- OpenAI SDK يستخدم OpenAI وAzure OpenAI وGroq، مع دعم Ollama محلي.
- Supabase Auth وPostgres وRow Level Security للحسابات ومساحات العمل.
- استخراج PDF عبر pdf.js وDOCX عبر Mammoth، بينما TXT وMD وJSON وCSV وHTML تعالج في المتصفح.
- Docker مبني على `node:22-bookworm-slim`.

## طريقة التشغيل والبناء

- التثبيت النظيف: `npm ci`.
- تشغيل الواجهة والخادم على أصل واحد: `npm start` أو `npm run rafid`.
- الواجهة فقط: `npm run frontend`.
- Azure Functions: `npm run azure` عند توفر أدوات Azure Functions Core Tools.
- لا توجد عملية تجميع للتطبيق نفسه؛ `npm run build:vendor` يعيد بناء عميل Supabase المحلي بواسطة esbuild.
- فحص JavaScript: `npm run check`، والاختبارات: `npm test`.

## حالة البناء والاختبارات

تم الفحص النهائي للأمر 2 على Node.js `v22.23.1` وnpm `10.9.8`:

- `npm ci`: ناجح من `package-lock.json`؛ 119 حزمة مثبتة و120 حزمة مدققة، وصفر ثغرات معلنة.
- `npm run check`: ناجح؛ فحص الصياغة لـ27 ملف JavaScript.
- `npm run typecheck`: ناجح بواسطة TypeScript compiler و`jsconfig.json`. المشروع JavaScript ولا يحتوي ملفات TypeScript؛ لذلك يتحقق compiler من إعداد المشروع ومصادر JavaScript دون تفعيل ترحيل `checkJs` الصارم الشامل.
- `npm run lint`: ناجح بواسطة ESLint 10 على الواجهة والخادم والسكربتات والاختبارات.
- `npm test`: ناجح؛ اختبارات الخادم، وعقود SDK، وSupabase، ومنطق الواجهة، وتدقيق الواجهة الثابت، واختبار smoke للخادم الموحد نجحت.
- `npm run build`: ناجح؛ يشغّل بناء vendor بواسطة esbuild، والناتج قابل للتكرار.
- `npm audit --audit-level=low`: ناجح لكل اعتماديات الإنتاج والتطوير؛ صفر ثغرات معلنة.
- التشغيل المحلي: نجح الخادم، وأعادت `/` حالة HTTP 200 ومحتوى `text/html` وصفحة HTML بعنوان موجود.
- `node scripts/ui-smoke.js`: فشل لأن Playwright غير مصرح به ضمن اعتماديات المشروع، كما أنه غير مشمول في `npm test`.
- لم يجر اختبار صورة Docker أو نشر Azure/Render فعليًا لعدم توفر أدواتها المحلية، ولا توجد GitHub Actions أو `render.yaml`.

## بنية الواجهة والخادم

### الواجهة

الواجهة تطبيق أحادي الصفحة بخمس حالات رئيسية: الفرصة، المشاريع، المحفظة/القرار، المراجعة، والإعدادات، إضافة إلى بوابة الدخول ونافذة الخصوصية. الملف `frontend/rafid-v4.js` يدير الحالة، المصادقة، الرفع، الاستخراج، استدعاء API، الحفظ والتصدير في ملف واحد كبير.

### API والخادم

المسارات الأساسية هي:

- `GET /api/rafid/public/config`
- `GET /api/rafid/health`
- `POST /api/rafid/local/configure` في الخادم الموحد فقط
- `POST /api/rafid/source/fetch`
- `POST /api/rafid/opportunity/extract`
- `POST /api/rafid/extract`
- `POST /api/rafid/opportunity/assess`

منطق Azure موزع على `src/functions/` و`src/lib/`، بينما يعيد `scripts/run-rafid.js` تنفيذ جزء معتبر منه محليًا، ما يخلق احتمال انحراف السلوكين.

## تدفق البيانات والتحليل

### Groq

- يستخدم OpenAI SDK مع `https://api.groq.com/openai/v1` ونماذج GPT-OSS.
- يطلب JSON Schema صارمًا ودرجة حرارة صفر، مع إعادة محاولة واحدة عند فشل المخطط.
- وضع `strict_zdr` يمنع الطلب إذا لم يؤكد إعداد البيئة سياسة عدم الاحتفاظ؛ أما الوضع القياسي فقد يسمح باحتفاظ المزود.
- يقص النصوص الطويلة إلى نحو 5–6 آلاف حرف ويحذف الوسط، ما قد يفقد الأدلة الحاسمة.

### Supabase

- الواجهة تستخدم عميل Supabase محليًا مع حفظ الجلسة وتجديدها.
- الخادم يتحقق من Bearer token عبر `/auth/v1/user` ويخزن النتيجة 30 ثانية.
- المتصفح يقرأ ويحدّث جدول `rafid_workspaces` مباشرة.
- المخطط يفعّل ويفرض RLS وسياسات ملكية المستخدم وحدًا لحجم مساحة العمل مقداره 1.5MB.

### رفع الملفات واستخراج النص

- المعالجة تتم في المتصفح، والحد 20MB لكل ملف دون حد صريح لعدد الملفات أو مجموع أحجامها.
- PDF يستخرج طبقة النص صفحة بعد صفحة بلا OCR؛ الملفات الممسوحة ضوئيًا لا تعمل جيدًا.
- DOCX يستخدم `extractRawText` وقد يفقد بنية الجداول والعناوين.
- الملفات المتعددة تعالج بالتتابع ثم تجمع، بينما حد جسم طلب الخادم 1.5MB.
- جلب الروابط يتم خادميًا بعد فحوص SSRF، لكنها غير مكتملة كما هو موضح في المخاطر.

### إنشاء نتيجة التحليل

يمر التدفق بثلاث مراحل: استخراج الفرصة بالذكاء الاصطناعي، استخراج المشروع بالذكاء الاصطناعي، ثم تقييم المطابقة بالذكاء الاصطناعي. بعد ذلك يطبق منطق حتمي بوابات الأهلية والفجوات؛ لكنه يعتمد على حالات وأدلة ولّدها النموذج، ولذلك لا يلغي عدم يقين المراحل السابقة.

## أسباب ضعف الأداء وعدم ثبات النتائج

1. لكل مشروع استدعاء استخراج ثم استدعاء تقييم بصورة متتابعة، كما أن دفعة المشاريع تنفذ بالتسلسل حتى عشرة مشاريع.
2. لا توجد مهلة أو إلغاء من جهة المتصفح، ولا مهلة صريحة لاستدعاءات الذكاء الاصطناعي.
3. قص النص بحذف الوسط يفقد سياقًا وأدلة، خصوصًا في كتيبات الفرص والملفات الطويلة.
4. ناتج نموذج أول يصبح مدخلًا لنموذج ثان، من دون مجموعة تقييم ذهبية أو قياس للتكرارية أو تثبيت نسخة prompt/model داخل النتيجة.
5. محددات المعدل والحصة اليومية وإعداد المزود وذاكرة الجلسات محلية لكل عملية؛ يعاد ضبطها عند إعادة التشغيل وتختلف بين النسخ المتعددة.
6. التحقق البعيد من Supabase يتكرر بعد انتهاء cache القصير، ما يزيد زمن الطلبات.

## التعقيد والملفات أو المكتبات غير المستخدمة

- `frontend/rafid-v4.js` و`scripts/run-rafid.js` و`src/lib/ai.js` كبيرة ومتعددة المسؤوليات.
- يوجد تنفيذان للخادم: Node موحد وAzure Functions، مع تكرار في التطبيع والتحقق والأخطاء وCORS وجلب المصادر.
- `frontend/rafid_v3_1_ai_connected.html` ملف قديم ضخم وقابل للوصول كأصل ثابت، ويتعارض محتواه المضمن مع CSP في الخادم الحالي.
- `rafid_v4_3_auth_callback_fixed.zip` نسخة مصدر مضاعفة ومتتبعة داخل Git.
- `frontend/rafid_v3_original_contract.json` و`frontend/vendor/pdf-legacy-bridge.mjs` يبدوان بقايا لمسار V3.
- `mammoth` و`pdfjs-dist` ضمن devDependencies لكن التشغيل يعتمد على نسخ vendor متتبعة، ولا توجد عملية بناء موثقة لهما.
- `scripts/ui-smoke.js` غير داخل سلسلة الاختبار ويعتمد على Playwright غير المعلن.

## التدقيق الأمني والأسرار

- أعيد الفحص في الأمر 4 على النسخة الحالية و10 commits قابلة للوصول ولقطات تاريخ `main`. لم يعثر الفحص على سر حي عالي الثقة. المطابقات الوحيدة كانت مفاتيح اختبار وهمية في `scripts/sdk-contract-test.js` ونسختها داخل ملف ZIP قديم؛ لم تعرض أي قيمة.
- تغير شكل مفاتيح الاختبار في المصدر حتى لا يشبه تنسيق المفاتيح الحقيقية. بقيت النسخة الوهمية القديمة داخل ZIP المتتبع، وهي ليست سرًا لكنها تظل مرشحًا للأرشفة/الإزالة في مرحلة التنظيف.
- أي رمز وصول سبق كشفه خارج المستودع يجب إلغاؤه وتدويره فورًا، بصرف النظر عن نتيجة فحص Git.
- `.gitignore` و`.dockerignore` و`.funcignore` تستبعد الآن ملفات `.env.*` والإعدادات المحلية ومجلدات الأسرار وملفات المفاتيح والشهادات؛ كما تستبعد حزمة Docker ملفات ZIP القديمة.
- أصبحت `.env.example` و`local.settings.example.json` تحتويان قيمًا فارغة أو وهمية فقط، مع أسماء موحدة للحدود والمهلة والمعدل.
- أضيف `src/lib/env.js` للتحقق المبكر الآمن من البيئة وإظهار أسماء المتغيرات ورموز الأخطاء فقط، دون قيمها. أخطاء Groq أو Supabase تجعل الخدمة التابعة غير جاهزة لكنها لا تمنع فتح الصفحات العامة.
- الواجهة تستقبل قائمة سماح عامة فقط: اسم التطبيق ورابطه وحد الملف وحالة الجاهزية وSupabase URL وanon key عند اكتمالهما. لا يقرأ أو يرسل `SUPABASE_SERVICE_ROLE_KEY`.
- بعد التغييرات نجحت `npm run check` و`npm run typecheck` و`npm run lint` و`npm test` و`npm run build`، بما فيها اختبارات حدود البيئة والصفحة العامة دون Supabase.
- الإعدادات الافتراضية تسمح بتعطيل المصادقة وCORS عام ووضع إعداد مزود محلي. نشرها خطأً كخدمة عامة قد يتيح استدعاءات مجهولة أو تغيير مفتاح المزود في ذاكرة العملية.
- حماية SSRF تفحص DNS قبل `fetch`، ما يترك احتمال DNS rebinding، كما أن فحص IPv4-mapped IPv6 لا يغطي كل النطاقات الخاصة/المحلية.
- مزامنة مساحة العمل قد تتضمن أدلة منظمة وهويات؛ تصنيف الحساسية وقرار الحفظ يفرضان من جهة العميل فقط، بلا سياسة خادمية أو سجل تدقيق واضح.
- مفتاح Supabase القابل للنشر في المتصفح مقصود، وتعتمد سلامته على استمرار صحة RLS وعدم تسريب service role.

## تجربة المستخدم وRTL والعربية

- الأساس جيد: `lang="ar"` و`dir="rtl"` وتسميات وskip link وبنية وصول مقبولة، ولم تظهر أخطاء console عند التحميل المحلي.
- في الهاتف تختفي وصلة الإعدادات عند عرض 920px أو أقل، مع أن الإعدادات ضرورية للوضع المحلي.
- عند 680px أو أقل تختفي أزرار العرض التجريبي والاستيراد والتصدير، فتضعف الاستعادة ونقل البيانات.
- شريط المراحل أعرض من الحاوية على هاتف بعرض 390px ويحتاج تمريرًا أفقيًا، وقد تختفي المرحلة الأخيرة بصريًا.
- حقل تنقيح الخصوصية مجبر على LTR ومحاذاة يسار، وهو غير مناسب للنص العربي.
- رسائل الأخطاء التقنية طويلة، ولا توجد مؤشرات تقدم تفصيلية أو إلغاء ومعالجة جزئية واضحة للدفعات الطويلة.

## مشكلات النشر على Render

- الخادم يرتبط افتراضيًا بـ`127.0.0.1`، بينما يلزم Render الربط بـ`0.0.0.0` واستخدام `PORT`. يتحقق ذلك فقط عند ضبط وضع النشر المشترك أو `RAFID_HOST` بصورة صحيحة.
- مسار `/api/rafid/health` محمي بالمصادقة، ولذلك يفشل كفحص صحة HTTP من Render؛ أما `/api/rafid/public/config` فليس فحص جاهزية فعليًا.
- لا يوجد `render.yaml` يثبت متغيرات التشغيل الآمنة، وأمر التشغيل، ومسار فحص الصحة.
- نظام الملفات المؤقت لا يضر بيانات المستخدم الحالية، لكن إعادة تشغيل العملية تصفر الحصص والذاكرة المحلية وإعداد المزود.
- الخطة المجانية قد تضيف cold start ملحوظًا إلى أول تحليل طويل.

## الاختبارات الموجودة والمفقودة

### الموجودة

- وحدات/تكامل خفيفة لمنطق الخادم، والتطبيع، وعقود OpenAI/Ollama/Groq.
- مصادقة Supabase والجلسات ومحدد المعدل.
- منطق الواجهة وتدقيق ثابت لعناصر UI.
- smoke للخادم الموحد وملفات vendor.

### المفقودة

- اختبار Supabase OAuth/RLS سلوكي كامل بحسابين مستقلين على بيئة الإنتاج.
- مجموعة حالات عربية ذهبية لقياس دقة الأهلية والأدلة والثبات بين التشغيلات.
- تشغيل Docker محلي مستقل؛ أما Render وفحص الصحة والرحلة الحية فقد تم التحقق منها على staging.
- E2E متصفح قابل للتشغيل، واختبارات الهاتف ولوحة المفاتيح وقارئ الشاشة.
- PDF ممسوح أو مشفر أو تالف، وملفات كثيرة/كبيرة، واستخراج عربي من PDF وDOCX.
- DNS rebinding وIPv4-mapped IPv6 وCORS والإعدادات الافتراضية غير الآمنة.
- إعادة التشغيل وتعدد النسخ والحصة الموزعة والاسترداد الجزئي والمهل.
- تكامل مسارات Azure Functions.

## خطة الإصلاح المرتبة

### حرج قبل الإطلاق

1. تدوير أي رمز وصول كشف خارج Git، وإكمال `.dockerignore` و`.funcignore`، ثم إعادة فحص الأسرار والصورة النهائية.
2. فرض إعداد إنتاج آمن: مصادقة مفعلة، origins محددة، Groq server-managed مع `strict_zdr` مؤكد، ومنع `local/configure` في النشر العام.
3. إضافة إعداد Render صريح للربط بـ`0.0.0.0` و`PORT`، ومسار صحة عام محدود لا يكشف بيانات ويختبر الجاهزية.
4. إغلاق ثغرات SSRF وإضافة اختبارات DNS rebinding والعناوين الخاصة والمشفرة.
5. إضافة مهلات وإلغاء وحدود لإجمالي الملفات والنص، واختبار رحلة واحدة كاملة على staging بحسابات المالك.
6. إنشاء CI لـ`npm ci` و`check` و`test` و`build:vendor` و`audit` ومنع دمج فشلها.

### مهم قبل الإطلاق

1. إعلان Playwright وتشغيل E2E حقيقي، مع إصلاح وصول الهاتف للإعدادات والإجراءات وشريط المراحل وحقل العربية.
2. بناء مجموعة تقييم عربية ذهبية وتسجيل نسخة النموذج/prompt وقياس ثبات النتيجة ودقة الأدلة.
3. تحسين استراتيجية التقسيم بدل حذف وسط النص، وإضافة OCR أو رفض واضح للملفات الممسوحة.
4. تقليل التسلسل في الدفعات ضمن حدود المزود، وإضافة تقدم وإلغاء واسترداد جزئي.
5. نقل الحصة ومحدد المعدل والإعدادات المؤثرة إلى مخزن مشترك قبل تعدد النسخ.
6. توحيد منطق Node وAzure أو تحديد مسار نشر واحد للنسخة الأولية.
7. فرض سياسة حفظ البيانات الحساسة خادميًا، وتوثيق الحذف والاحتفاظ وسجل التدقيق.

### يمكن تأجيله

1. دعم مزودين متعددين وAzure/Ollama في واجهة الإنتاج العامة.
2. OCR المتقدم والصيغ الإضافية بعد إثبات استخدام PDF/DOCX/TXT الأساسي.
3. إعادة هيكلة شاملة للواجهة إلى إطار عمل؛ يكفي أولًا فصل الوحدات الحرجة واختبارها.
4. إزالة/أرشفة V3 والـZIP والعقود القديمة بعد التأكد من عدم اعتماد تشغيل أو عميل عليها.
5. توسيع الأدوار والتقارير ولوحات القياس لما بعد تجربة MVP.

## أقل نطاق ممكن لنسخة أولية جيدة

- فرصة تمويل حقيقية واحدة، و5–10 مشاريع، ومراجع بشري إلزامي.
- مزود واحد فقط: Groq بمفتاح خادمي ووضع `strict_zdr` مؤكد.
- Supabase Auth وRLS ومساحة عمل واحدة لكل مستخدم.
- خدمة Render واحدة same-origin للواجهة وAPI.
- إدخال رابط أو PDF/DOCX/TXT، ثم استخراج الفرصة والمشروع، تقييم الأهلية، مراجعة الأدلة والفجوات، وتصدير القرار.
- لا يتضمن النطاق العام تعدد المزودين أو Azure/Ollama أو V3 أو أدوارًا معقدة أو دفعات أكبر من عشرة مشاريع.

- نجحت إعادة الاختبار الحي بعد استرداد الأقسام العربية دون fallback: أصبحت الدرجة الحتمية 45 بدل 15، وتغطية الأدلة 21 بدل 7، وسجل المراجع الثاني تصحيحًا واحدًا؛ بقيت الأهلية «غير محسومة» لغياب دليل الجهة، وهو القرار المحافظ الصحيح.
- تحسن زمن الرحلة الحية في الجولة النهائية من نحو 191 ثانية إلى نحو 151 ثانية (استخراج الفرصة 7.6 ث، البحث 94.1 ث، والتقييم 49.2 ث) دون الانتقال إلى نموذج أصغر.

## تحديث 10 أغسطس 2026 — اكتشاف الفرص والمحفظة المؤسسية

- تحولت خدمة «اكتشف الفرص المناسبة» من بطاقة قادمة إلى رحلة كاملة: نص أو ملف بحث، استخراج منظم مرة واحدة، ثم ترتيب حتمي لكتالوج فرص موثق المصدر.
- أضيف كتالوج أولي لمسارات منح RDIA التي تظهر في صفحة التمويل والدليل الرسمي، مع رابط رسمي وتاريخ تحقق وحالة محافظة «تحقق من المصدر الرسمي» بدل الادعاء بأن الدعوة مفتوحة.
